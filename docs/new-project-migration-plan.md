# 新工程迁移风险评估与实施方案

## 1. 迁移目标

目标不是重写项目，而是在**不影响当前旧项目正常运行**的前提下，新建一个使用正式项目名的新工程目录，作为后续独立维护和分发的主目录。

建议的新目录名：

- `D:\myapp\ai_program\x-growth-task-coach`

建议的新工程英文名：

- `x-growth-task-coach`

当前对外产品名保持不变：

- 中文：`X 增长助手`
- 英文：`X Growth Task Coach`

---

## 2. 这个方案是否现实

结论：

> 现实，而且可以做得比较稳，但必须按“复制迁移”而不是“原地改目录”的方式做。

原因：

- 当前项目已经基本可用，直接原地改目录风险太高
- 当前项目里有大量路径、脚本、文档引用，如果直接重命名旧目录，容易把正在用的环境搞乱
- 复制出一个新工程目录，再在新目录里做统一清理，旧项目可以继续原样保留，风险最低

所以这次应该采用：

### 正确迁移方式

1. 保留旧目录不动
2. 复制出一个新目录
3. 在新目录里统一工程名和相关元信息
4. 单独验证新目录能正常构建和加载
5. 确认新目录稳定后，再决定以后主要在哪个目录继续开发

---

## 3. 不应该采用的方式

这次不建议用下面这些做法：

### 3.1 直接重命名旧目录

不建议把：

- `D:\myapp\ai_program\tmp\twitter-web-exporter`

直接改成：

- `D:\myapp\ai_program\x-growth-task-coach`

原因：

- Chrome 已加载扩展目录会失效
- 本地文档里的绝对路径会全部失效
- 自动化脚本里的固定路径会失效
- 当前 Git 工作区和你已有操作习惯会被打断

### 3.2 先删旧目录，再新建新目录

不建议。

原因：

- 一旦迁移中有遗漏，没有旧目录可回退
- 当前你还处在可以试用、可以继续修补的阶段，不应该先砍掉旧基座

### 3.3 新建一个全新空项目再手工搬模块

不建议。

原因：

- 成本高
- 极容易漏逻辑
- 这不是必要迁移方式

---

## 4. 已确认会受影响的内容

下面这些是我已经实际查到、迁移时必须考虑的地方。

### 4.1 Git 远程

当前旧项目 Git 远程：

- `origin`: `https://github.com/JadeLiang003/x-growth-task-coach.git`
- `upstream`: `https://github.com/prinsss/twitter-web-exporter.git`

含义：

- 你自己的 GitHub 仓库已经是正确的
- 所以迁移新目录时，不需要重新找仓库
- 只需要决定新目录是否继续沿用同一个 `.git`

---

### 4.2 构建输出路径

文件：

- `vite.extension.config.ts`

当前：

- 输出目录：`dist/extension`

影响：

- 这个路径是**相对项目根目录**的
- 迁移到新目录后不会天然出错
- 所以构建输出这块本身不是主要风险点

结论：

- **构建配置可以直接沿用**

---

### 4.3 自动化脚本中的项目目录引用

我已经查到至少有一个脚本写了旧目录名：

文件：

- `scripts/automation/diagnose-real-article-publish.mjs`

问题：

- 里面包含 `tmp/twitter-web-exporter/...` 这样的路径

影响：

- 迁到新目录后，这类脚本如果继续使用旧路径，会把诊断结果写回旧目录

结论：

- 自动化脚本要做一次**项目路径审查**
- 至少要改掉明确写死旧目录名的脚本

---

### 4.4 文档里的绝对路径

我已经查到文档里大量存在旧绝对路径，例如：

- `D:/myapp/ai_program/tmp/twitter-web-exporter/...`
- `tmp/twitter-web-exporter/...`

重点文档包括：

- `docs/plugin-user-guide.md`
- 多个 phase 文档
- 多个内部分析文档

影响：

- 新目录迁移后，这些文档里的绝对路径链接会继续指向旧目录
- 特别是 `plugin-user-guide.md` 里插图路径也写死了旧目录

结论：

- **对外主说明文档必须修**
- 旧的 phase 文档可以后处理，不必一次清完

---

### 4.5 工程元信息

文件：

- `package.json`
- `package-lock.json`
- `bun.lock`

当前仍然是：

- `twitter-web-exporter`

影响：

- 新目录如果还保留旧工程名，会继续造成混乱

结论：

- 新目录迁移后，必须同步改成：
  - `x-growth-task-coach`

---

### 4.6 导出数据库文件名

文件：

- `src/core/settings.tsx`

当前仍然会导出：

- `twitter-web-exporter-时间戳.json`

影响：

- 用户会直接看到旧项目名

结论：

- 这是迁移后必须一起改掉的用户可见项

---

### 4.7 日志前缀

文件：

- `src/utils/logger.ts`

当前：

- `[twitter-web-exporter]`

影响：

- 主要影响开发和排障，不直接影响普通用户

结论：

- 不是第一优先级
- 但如果你希望新目录彻底独立，建议在新目录里一起改掉

---

## 5. 风险分级

### 低风险

- 新建一个新目录副本
- 修改 `package.json`
- 修改锁文件名字
- 修改导出数据库文件名
- 修改说明文档中主图片路径

### 中风险

- 修改自动化脚本里写死的旧路径
- 修改 README / 使用说明中的旧绝对路径
- 修改日志前缀

### 高风险

- 直接重命名旧目录
- 在原目录上边改边迁
- 迁移时顺手改大量业务代码

---

## 6. 推荐迁移策略

这次推荐采用：

## 策略：双目录并行迁移

### 旧目录

保留：

- `D:\myapp\ai_program\tmp\twitter-web-exporter`

用途：

- 作为稳定回退版本
- 迁移过程中不动它

### 新目录

新建：

- `D:\myapp\ai_program\x-growth-task-coach`

用途：

- 新的正式工程目录
- 后续逐步切换到这个目录继续维护

## 8. Git 策略建议

这里有两种做法。

### 方案 A：复制目录时保留 `.git`

优点：

- 新目录直接延续当前仓库历史
- 继续推送到你现在的 GitHub 仓库最方便

缺点：

- 本机上会同时存在两个指向同一个 Git 仓库历史的工作目录
- 如果你同时在两个目录改，很容易混乱

### 方案 B：复制目录时不带 `.git`，新目录重新初始化 Git

优点：

- 新旧目录完全隔离
- 不容易误操作

缺点：

- 需要重新连远程
- Git 历史不会默认跟过去

### 我建议

这次更稳的是：

> **迁移阶段先保留 `.git`，但明确规定只在新目录继续开发，旧目录只作回退参考**

原因：

- 你当前 GitHub 仓库已经正确
- 不需要重复初始化仓库
- 后续切换成本最低

---

## 9. 迁移实施顺序

建议严格按下面顺序做：

### 第一步：复制项目

从：

- `D:\myapp\ai_program\tmp\twitter-web-exporter`

复制到：

- `D:\myapp\ai_program\x-growth-task-coach`

要求：

- 旧目录保持不动
- 新目录作为独立工作副本

### 第二步：只在新目录统一工程名

只改：

- `package.json`
- `package-lock.json`
- `bun.lock`
- `src/core/settings.tsx`
- `docs/plugin-user-guide.md`
- 路径写死的自动化脚本

### 第三步：重新构建

在新目录执行构建，确认：

- 能正常 build
- `dist/extension` 正常生成

### 第四步：重新加载扩展

在 Chrome 里用**新目录的构建产物**重新加载扩展

不要继续指向旧目录。

### 第五步：实际验证

至少验证这些：

- popup 是否能打开
- 设置页是否能打开
- 每日打卡是否正常
- 每日复盘是否正常
- 账号工作台是否正常
- 数据导出文件名是否已更新

### 第六步：确认切换

新目录稳定后，再决定：

- 后续开发是否只在新目录进行
- 旧目录是否转为只读备份

---

## 10. 迁移完成标准

只有同时满足下面这些，迁移才算完成：

1. 新目录能独立构建成功
2. 新目录加载到 Chrome 后功能正常
3. 用户界面仍然显示：
   - `X 增长助手`
   - `X Growth Task Coach`
4. 导出文件名不再含 `twitter-web-exporter`
5. `package.json` 不再含旧工程名
6. 主说明文档里的图片和路径不再依赖旧目录
7. 旧目录仍然可以保留并正常打开，作为回退版本

---

## 11. 最终建议

结论很明确：

> 可以迁，而且应该迁成“新目录并行”的方式，而不是直接动旧目录。

如果你现在要做这件事，最稳的方式不是“改名旧目录”，而是：

1. 保留旧目录
2. 复制出 `D:\myapp\ai_program\x-growth-task-coach`
3. 只在新目录做工程名统一
4. 在新目录构建和验证
5. 验证稳定后再切换主工作目录

这样做，既能得到一个真正属于你自己名字的工程目录，也不会把当前可用的旧项目搞坏。
