# Phase 7 账号工作台优化方案

更新日期：2026-05-14

## 1. 这份文档的目的

这份文档用于修正当前 `Phase 7` 在账号管理上的几个关键问题：

1. `big_creator` 作为主标签过于模糊，且容易误判
2. 候选池和账号池割裂，操作链路不顺
3. 角色标签、影响力标签、处理状态混在一起，用户难以理解
4. 当前筛选区像表单，不像工作台
5. 标签不够醒目，用户无法快速判断“这个账号是谁、属于哪类、值不值得优先处理”

这份文档不改代码，只定义下一轮开发应该如何收口。

---

## 2. 这轮优化的核心结论

这轮最重要的决定有 4 个：

1. 不再使用 `大 V` 作为主分类标签
2. 把“角色标签”和“影响力标签”彻底拆开
3. 候选池和账号池不做硬合并，改成统一的“账号工作台”
4. 标签视觉权重提升到仅次于用户名，成为列表里的第二关键信息

---

## 3. 信息模型重构

后续账号相关信息统一拆成 3 层。

### 3.1 处理状态

这是工作流状态，不代表账号类型。

建议固定为：

1. `待处理`
2. `已入池`
3. `已忽略`

补充说明：

- `观察中` 不再作为正式角色标签
- `观察中` 改成一种默认状态语义
- 也就是：账号在 `待处理` 状态下，本质上就是“观察中”

### 3.2 角色标签

这是账号“为什么值得你保留”的标签。

建议收缩为 3 个正式角色标签：

1. `同生态`
2. `对标学习`
3. `选题来源`

默认不再保留：

- `big_creator`
- `potential_mutual`
- `competitor`

原因如下：

#### `同生态`

解决的问题是：

- 今天该优先和谁互动
- 哪些账号和你面对相近用户、相近话题、相近问题

适合长期互动、建立认知和建立关系。

#### `对标学习`

解决的问题是：

- 向谁学内容结构
- 向谁学选题
- 向谁学表达方式和节奏

这类账号不一定是高频互动对象，但很适合拆解和复盘。

#### `选题来源`

解决的问题是：

- 从谁那里拿问题
- 从谁那里拿案例
- 从谁那里拿评论区语言和内容灵感

这类账号不一定要频繁互动，但很适合持续观察。

### 3.3 影响力标签

这是量级标签，不再使用“大 V / 非大 V”这种模糊表述。

#### 最终建议分层

考虑到插件核心适用范围是 `0-5k`，同时又要兼顾用户向上观察更大账号，我建议用 6 档：

1. `0-500`
2. `500-1k`
3. `1k-5k`
4. `5k-10k`
5. `10k-20k`
6. `20k+`

#### 为什么这样分

这个分法不是平台通用标准，而是面向当前产品阶段的工作分层。

理由如下：

1. `0-500`
   这一档通常是刚起号或还没形成稳定分发的账号，和你在冷启动阶段最接近

2. `500-1k`
   这是一个很常见的小跨越，通常已经有了一点反馈，但还没有进入更明显的放大阶段

3. `1k-5k`
   这是当前插件最核心的主战场，需要单独成档

4. `5k-10k`
   已经明显高于当前核心用户，但还不属于特别远的头部对象，适合重点借势和观察

5. `10k-20k`
   这是更成熟的一层，和 `5k-10k` 放在一起会过粗，所以单独拆出

6. `20k+`
   进入明显头部区间，适合单独标记

#### 为什么不继续用之前的 5 档

之前的：

- `0-300`
- `300-1k`
- `1k-5k`
- `5k-20k`
- `20k+`

问题在于：

- `0-300` 对真实使用来说有点窄
- `5k-20k` 跨度太大

所以这次修正为：

- 低端放宽到 `0-500`
- 中高端拆成 `5k-10k` 和 `10k-20k`

这样更均衡。

## 4. 新的账号工作台结构

### 4.1 总原则

候选池和账号池不做硬合并。

但它们也不应该继续作为两个割裂的区块出现。

正确做法是：

> 做成一个统一入口的“账号工作台”，内部按状态切换。

### 4.2 工作台视图

建议统一成 4 个视图入口：

1. `全部`
2. `待处理`
3. `已入池`
4. `已忽略`

解释：

- `待处理` 承接今天刚抓到、还没决定怎么处理的候选账号
- `已入池` 承接已经确认要长期跟进的账号
- `已忽略` 承接暂时不需要的账号
- `全部` 用于全局搜索和回看

### 4.3 为什么不建议真合并

因为候选账号和正式账号不是同一种生命周期。

候选账号更像：

- 临时原材料
- 待判断对象
- 噪音更高

正式账号更像：

- 已确认工作对象
- 会长期参与互动推荐和半自动记账

如果真合并成一张平表，后面只会越来越乱。

所以最合理的方案是：

- 入口合并
- 数据语义不合并
- 状态流转清楚

## 5. 工作台里的核心操作

### 5.1 `待处理`

允许：

1. 指定角色标签
2. 直接加入账号池
3. 批量加入账号池
4. 标记忽略
5. 查看建议理由
6. 打开主页

### 5.2 `已入池`

允许：

1. 修改角色标签
2. 修改影响力标签
3. 修改优先级
4. 重新打回待处理
5. 标记忽略
6. 查看最近互动时间
7. 打开主页

### 5.3 `已忽略`

允许：

1. 恢复为待处理
2. 直接加入账号池
3. 查看忽略前的建议信息

### 5.4 一个重要原则

“已导入”绝不能变成死状态。

也就是说，账号一旦进入 `已入池`，仍然必须继续可操作。

否则用户会感觉：

- 看得见
- 但改不了
- 也没法顺着管理

这是当前版本最明显的不合理点之一。

## 6. 角色判断逻辑怎么收紧

这轮不再追求“系统一上来就完全判对”。

建议规则改成：

### 6.1 系统先做角色建议

系统只建议这 3 种：

1. `同生态`
2. `对标学习`
3. `选题来源`

没有足够信号时，不直接乱判，保持“待处理”。

### 6.2 建议角色的判断依据

建议优先依据：

1. bio 关键词
2. overlay 关键词
3. 账号内容定位信号
4. 来源
5. 是否更适合作为互动对象、学习对象或选题对象

### 6.3 不再用这些做顶层角色

不再用作主角色的包括：

1. `big_creator`
2. `potential_mutual`
3. `competitor`

它们的问题分别是：

- `big_creator` 是量级，不是角色
- `potential_mutual` 是关系猜测，不是稳定角色
- `competitor` 太主观，也不稳定

## 7. 影响力标签怎么使用

### 7.1 展示层

影响力标签直接展示数值区间，不再展示“大 V”。

例如：

- `0-500`
- `500-1k`
- `1k-5k`
- `5k-10k`
- `10k-20k`
- `20k+`

### 7.2 交互层

影响力标签用于：

1. 筛选
2. 排序
3. 推荐优先级参考
4. 辅助你判断互动难度和学习价值

### 7.3 不直接替代角色标签

影响力标签不能代替角色标签。

一个账号完全可以是：

- `同生态 + 1k-5k`
- `同生态 + 10k-20k`
- `对标学习 + 20k+`
- `选题来源 + 500-1k`

也就是说：

- 角色回答“这个人对你有什么用”
- 影响力回答“这个人的量级有多大”

## 8. 界面优化方案

这部分按“统一工作台”来重构，不再延续当前一行一个筛选项的表单式布局。

同时，这部分会明确采用 `frontend-design` 的方向：让最关键的识别信息更强、更快被看到。

### 8.1 页面结构

建议结构为：

1. 顶部概览条
2. 吸顶筛选工具条
3. 主列表区
4. 行内展开区或侧边详情区

### 8.2 顶部概览条

顶部只放 4 个关键数字：

1. `待处理`
2. `已入池`
3. `已忽略`
4. `高优先级`

作用是让用户先知道当前积压和工作量。

### 8.3 吸顶筛选工具条

#### 第一行：高频筛选

只放最常用的：

1. 搜索框
2. 状态切换
3. 来源切换
4. 清空筛选

#### 第二行：标签筛选

这一行改成 chip 式标签，不再一行一个下拉框。

建议放：

1. 角色标签 chips
   - `同生态`
   - `对标学习`
   - `选题来源`

2. 影响力标签 chips
   - `0-500`
   - `500-1k`
   - `1k-5k`
   - `5k-10k`
   - `10k-20k`
   - `20k+`

3. 排序下拉
   - 最近更新
   - 粉丝量级
   - 优先级

这样会比“处理状态一行、来源一行、建议标签一行、置信度一行”清楚得多。

## 9. 列表卡片怎么改

这部分是这轮界面优化最重要的点。

### 9.1 标签视觉权重必须上移

用户名称仍然是第一信息。

但标签必须成为第二信息。

也就是说，一条账号卡片的优先级应该是：

1. 用户名 / handle
2. 角色标签 + 影响力标签
3. 状态 / 来源
4. 建议原因摘要
5. 低频操作

### 9.2 标签展示原则

标签不应该再像弱提示文字。

应该改成清晰的标签框，且并排展示。

建议形式：

1. 角色标签
   - 更高对比度
   - 更明显
   - 永远靠前

2. 影响力标签
   - 同样是清晰的实体标签
   - 紧跟在角色标签后面

3. 来源标签
   - 保留，但视觉权重略低于前两者

### 9.3 为什么要这样设计

因为用户在这页最核心的问题不是：

- 这段 bio 写了什么

而是：

- 这个人是哪类
- 量级多大
- 我现在要不要处理

所以标签必须高可见。

### 9.4 单条卡片建议结构

默认收成两层：

#### 第一层

- 用户名
- handle
- 角色标签
- 影响力标签
- 状态标签

#### 第二层

- 来源
- 建议原因一句话
- 最近更新时间
- 快速操作按钮

展开后再看：

- bio
- 详细建议理由
- 最近互动记录
- 更多操作

## 10. 批量处理怎么安排

### 10.1 原则

批量操作不要塞进筛选区下面堆成按钮墙。

更合理的方式是：

- 勾选后浮出批量操作条

### 10.2 批量操作建议保留这些

1. 批量标记为 `同生态`
2. 批量标记为 `对标学习`
3. 批量标记为 `选题来源`
4. 批量加入账号池
5. 批量忽略
6. 批量恢复待处理

### 10.3 不建议继续保留的批量导入表达

后续不建议继续出现：

- `全部导入为大 V`
- `全部导入为潜在互关`

因为这两个标签模型已经不稳了。

## 11. 下一轮开发的优先级

### P0

1. 去掉 `大 V` 作为主标签
2. 新增影响力分层字段
3. 角色标签收缩为：
   - `同生态`
   - `对标学习`
   - `选题来源`
4. `观察中` 改为默认状态语义

### P1

1. 候选池和账号池改成统一工作台
2. 已入池账号继续可操作
3. 顶部筛选区改成双层工具条
4. 标签视觉提升为第二关键信息

### P2

1. 批量处理条优化
2. 排序与筛选进一步细化
3. 详情面板优化

---

## 12. 验收标准

如果按这份方案开发，最终至少应满足：

1. 页面上不再出现 `大 V` 作为主分类
2. 每个账号都能同时看到：
   - 角色标签
   - 影响力标签
   - 处理状态
3. 候选账号和正式账号能在同一个工作台中管理
4. 已入池账号仍然可以继续改角色、改状态、改优先级
5. 筛选区不再是一行一个表单控件，而是紧凑的工具条结构
6. 标签在视觉上明显，仅次于用户名
7. 批量操作围绕新标签模型展开，不再围绕 `大 V` 展开
