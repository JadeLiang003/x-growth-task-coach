# Phase 7.9 内容识别与账号工作台优化方案

## 1. 这轮先解决什么

这轮不加新功能，先解决两个核心问题：

1. 内容识别不稳定  
   - 短内容有时被误判成长文  
   - 长文发布后有时不加一  
   - 自动保存和真正发布没有被清楚地区分

2. 账号工作台结构还不够统一  
   - `待处理 / 已入池 / 已忽略` 三个状态的工具条和卡片语言不统一  
   - 搜索栏、筛选栏、批量模式入口层级重复  
   - 已入池卡片展示信息和待处理卡片不一致  
   - “手动补充正式账号”放在已入池列表内部，位置不合适

---

## 2. 评估结论

### 2.1 内容识别的根因

当前长文识别还不稳定，核心不是“有没有监听到请求”，而是“**什么请求才代表真正发布成功**”这件事没有被严格定义。

现在的实现仍然混用了几种信号：

- 当前是不是在文章编辑页
- 最近是否点击过发布按钮
- 当前是不是 `CreateTweet / CreateNoteTweet / CreateArticle`
- 请求里有没有文章字段

这套信号组合能覆盖一部分情况，但仍然会出现两个问题：

1. 自动保存或草稿同步，和真正发布太像  
2. 不同账号或不同实验流量下，文章发布链路不一定完全一致

所以这轮不能继续只靠“页面上下文 + 猜测”。  
要改成：**显式发布意图 + 成功请求确认 + 一次性记账**。

### 2.2 账号工作台的根因

当前工作台的问题不是功能不够，而是信息架构还没有彻底收干净。

现在有几类重复：

- 顶部状态切换和筛选条分层不清
- 搜索框已经全局化了，但布局和后面的筛选控件视觉不统一
- “进入批量模式”按钮单独占一行，破坏了工具条节奏
- 待处理卡片和已入池卡片像两套不同产品

这说明下一轮应该先统一“工具条”和“卡片语言”，再决定局部细节。

另外，当前方案里还有一个实施前就能预见的风险：

- 如果把 `待处理 / 已入池 / 已忽略`
- 搜索框
- 来源筛选
- 标签筛选
- 粉丝量级筛选
- 批量模式入口

全部硬塞进同一行，虽然看起来“更省空间”，但层级会乱。

从产品视角看，它们属于不同层：

- `待处理 / 已入池 / 已忽略`：视图切换
- 搜索框：主入口
- 来源 / 标签 / 粉丝量级：筛选器
- 批量模式：操作模式切换

所以这轮不能只追求“收紧”，还要先把层级分清。

## 3. 开源参考与复用策略

这轮不再继续“小修小补猜规则”，而是明确参考开源项目已有的思路。结论不是直接整仓照搬，而是**分层复用**：

- **发布前 composer 判断**：借现成扩展的内容脚本检测方式  
- **页面内 GraphQL 拦截**：沿用现有仓库和成熟扩展的 page-world 注入方式  
- **发布成功记账**：改成“界面状态 + 网络确认”的双条件  
- **账号工作台布局**：继续按统一工具条和统一列表视图来收

这轮我重新参考了三个外部方向：

### 3.1 `x-algorithm-score`

来源：  
[x-algorithm-score](https://github.com/affaan-m/x-algorithm-score)

可借鉴点：

- 页面内轻悬浮入口
- 回复 / 引用 / 新发帖区分清楚
- composer 检测和页面注入是清晰分层的
- 内容脚本专注于“当前正在写什么”，而不是直接替代发布逻辑

不直接照搬的原因：

- 这个项目重点是“发帖前评分”，不是“发帖后记账”
- 它没有直接解决 `Article` 真正发布成功后的记账问题

### 3.2 `twitter-web-exporter`

来源：  
[twitter-web-exporter](https://github.com/prinsss/twitter-web-exporter)

可借鉴点：

- 明确走**页面世界注入**，而不是只在扩展隔离环境里做猜测
- 通过拦截 X 站内 GraphQL / XHR / fetch 链路拿到真实请求数据
- 这种方式更适合做“最终到底发了什么”的识别

对我们最有价值的不是导出功能，而是这条工程路线：

1. 内容脚本只负责挂载和桥接
2. 真正的请求拦截发生在页面上下文
3. 识别逻辑尽量依赖真实请求，而不是只看 DOM

这条思路是这轮识别重构的主参考。

### 3.3 `x-search-pro`

来源：  
[x-search-pro](https://github.com/neonwatty/x-search-pro)

可借鉴点：

- Sidebar + popup 的分工清楚
- 搜索库是“一个工作台 + 分类过滤 + 即时搜索”
- 强调 `Instant search`、`Sidebar + popup`、`Per category count`

对我们最有价值的不是视觉，而是这几个结构信号：

- 一个统一工具条
- 状态切换和筛选不分裂
- 搜索是全局入口，不是局部输入框

### 3.4 工程层补充参考

参考：  
[Chrome 扩展内容脚本文档](https://github.com/GoogleChrome/developer.chrome.com/blob/main/site/en/docs/extensions/mv3/content_scripts/index.md)

可借鉴点：

- 内容脚本运行在隔离世界
- 如果要稳定改写页面里的 `fetch / XHR`，就应该用**注入到页面世界的桥接脚本**

这说明我们后面不应该继续靠“纯 content script 猜网络”，而应该坚定走：

- content script 挂桥
- page bridge 拦请求
- background 记账

### 3.5 结论

这轮不再继续凭感觉微调，技术方向明确按下面三条执行：

- 内容识别：更接近“真实发布确认”，优先借 `twitter-web-exporter` 的页面请求拦截路线
- 工具条结构：更接近 `Linear + GitHub Issues`
- 搜索/侧栏组织：吸收 `x-search-pro` 的统一搜索工作台思路

## 4. 下一轮修改方案

## 4.1 内容识别：改成“发布确认制”

### 目标

- 短内容不再误判成长文
- 长文只有真正发布后才加一
- 自动保存、草稿同步、编辑中间态都不计数

### 新规则

#### 规则 A：长文只认 `Article`

- 继续保留产品定义：
  - `Article` = 长文
  - 明确线程 = 线程
  - 其他原创 = 短内容

#### 规则 B：长文只在“显式发布成功”后记一次

长文计数必须同时满足：

1. 当前处于文章编辑页
2. 用户触发了明确的发布动作
3. 后续收到匹配的成功发布请求
4. 该发布会话还没有记过账

不满足以上条件时：

- 自动保存不记
- 草稿同步不记
- 编辑过程中的中间请求不记

#### 规则 C：短内容默认回到最保守定义

- 非 `Article`
- 非明确线程
- 只要是正常原创成功发布
- 就统一算短内容

### 实现思路

这轮不再继续用“长文章页里最近 15 秒发生过什么”这种模糊窗口作为核心判定。

改成更清楚的**双阶段识别模型**：

#### 第一层：composer 模式识别

借 `x-algorithm-score` 的思路，把当前创作模式先分清：

- 普通发帖
- 回复
- 引用
- 文章编辑

这一层负责回答：

> 用户现在正在做哪种创作动作

#### 第二层：发布成功确认

借 `twitter-web-exporter` 的页面请求拦截思路，只在页面世界里看真实网络链路。

这一层负责回答：

> 这次动作到底有没有真正发布成功

所以最终记账必须同时满足：

1. 当前是文章编辑模式
2. 用户触发了显式发布动作
3. 页面世界里捕获到对应的成功发布请求
4. 这次发布会话还没记过账

改成更清楚的发布会话模型：

1. 建立 `articlePublishSession`
   - `idle`
   - `armed`
   - `published`

2. 用户点发布按钮时，进入 `armed`

3. 只有在 `armed` 状态下，命中成功发布请求，才记一次长文

4. 一旦成功记账，立刻进入 `published`，同一会话不再重复加数

5. 如果只是自动保存，则不进入 `published`

### 额外补充

为了避免继续盲修，这轮要加一个临时调试视图，仅供开发验证：

- 最近 20 条发帖相关请求
- 每条记录：
  - endpoint
  - 当前页面路径
  - 是否处于文章会话
  - 是否被判为发布成功
  - 最终记成短内容 / 长文 / 线程 / 忽略

这块只作为开发和验收使用，不暴露给普通用户。

### 这轮的明确复用原则

为了避免继续重复造轮子，这轮识别部分按下面的复用原则执行：

1. **不自己再发明“页面里猜用户是不是发了长文”的新规则**
2. **优先借 page-world 请求拦截路线**
3. **优先借 composer 状态检测路线**
4. **最终只保留我们自己的业务映射**
   - `Article -> 长文`
   - `Thread -> 线程`
   - 其他原创 -> 短内容

---

## 4.2 账号工作台：改成真正统一的工具条

### 目标

- `待处理 / 已入池 / 已忽略` 共享同一个搜索和筛选体系
- 工具条不再分裂成两三层
- 批量模式不再单独占一行
- 卡片语言统一

### 新结构

#### 第一层：主工具条

这一层只放高频主动作：

1. 状态切换
   - `待处理`
   - `已入池`
   - `已忽略`

2. 全局搜索框
   - 切换状态时搜索词保留
   - 这是整个工作台的主入口

3. 批量模式切换
   - 不再是普通按钮
   - 而是一个明确的“模式开关”

4. 手动添加账号
   - 作为全局动作入口
   - 不埋进某个列表内部

#### 第二层：筛选条

这一层只放筛选器：

1. 来源筛选
   - 全部来源 / Following / Followers

2. 标签筛选
   - 全部标签 / 同生态 / 对标学习 / 待判断

3. 粉丝量级筛选
   - 统一保留
   - 无数据时自然显示为空结果，不做额外解释块

4. 清空筛选
   - 轻量文字按钮或次级按钮

### 设计原则

- 状态切换和筛选器必须分层
- 搜索是主入口，筛选是辅助入口
- 批量模式属于“状态切换”，不是普通动作按钮
- 不再出现“状态切换一行、筛选一行、批量模式又一行”的碎裂结构

---

## 4.3 批量模式：保留，但按需展开

### 目标

- 继续保留大批量处理能力
- 平时不增加界面噪音

### 新规则

默认状态：

- 不显示复选框
- 卡片直接操作

进入批量模式后：

- 才显示复选框，或者更好一点，点击卡片就能选择，已经选择的卡片出现边缘高亮等类似的提示，方便用户点击。
- 才显示批量操作条
- 工具条右侧的“批量模式”状态明显变化

### 批量条建议

只保留这些动作，并且按用户操作顺序排列：

1. `已选 N 个`
2. `全选当前页`
3. `全选筛选结果`
4. `清空`
5. 分隔
6. `加入账号池`
7. `设为同生态`
8. `设为对标学习`
9. `忽略 / 恢复`
10. `退出批量模式`

不再把“批量条”放成和筛选条抢层级的独立面板。

---

## 4.4 手动补充正式账号：从列表内部挪出来

### 当前问题

现在“手动补充或编辑正式账号”放在已入池列表内部，语义不够稳。

它看起来像：
- 某个列表项的一部分

但实际上它是：
- 全局动作入口

### 新建议

把它移到账号工作台右上角，作为一个全局入口：

- `手动添加账号`

点击后再展开：

- 折叠区
- 或抽屉
- 或轻量弹层

### 编辑逻辑

当用户点击某张卡片的“编辑”时：

- 自动打开这个表单
- 自动带入当前账号信息
- 不再让用户自己去找表单位置

这会比现在顺得多。

---

## 4.5 卡片语言统一

### 目标

待处理和已入池看起来像同一个产品，而不是两套页面。

### 统一卡片结构

每张卡片都尽量保持：

1. 名称 + 标签
2. handle
3. bio（优先显示）
4. 辅助信息：
   - 粉丝数 / 粉丝量级
   - 来源
   - 最近互动时间
5. 操作区

### 需要删掉的内容

- “量级明显更高”
- “更适合作为对标学习对象”
- 泛泛的建议理由文案

这些话对判断和执行帮助不大，应该退到次要层，甚至直接去掉。

---

## 4.6 粉丝与标签展示统一

### 当前问题

- 待处理里能看到具体粉丝数
- 已入池里只有量级，没有具体粉丝数

这会让信息层级不统一。

### 新建议

如果候选数据里已经抓到粉丝数：

- 已入池卡片优先展示具体粉丝数
- 同时保留量级标签

如果没抓到具体粉丝数：

- 再只显示量级

也就是说：

- **具体数字优先**
- **量级标签辅助**

这条规则待处理、已入池、已忽略三种状态都一致执行，不再出现一边看得到具体数、一边只能看量级的情况。

---

## 4.8 popup 每日复盘：改成“可直接发推”的复盘版

### 当前问题

现在的每日复盘方向是对的，但有三个明显问题：

1. 更像系统总结，不像可直接发的推文
2. 句子太密，信息太挤，缺少自然断句
3. 用户补充了最佳帖子 URL / 最佳回复 URL，但复制出去时价值不明显

从产品角度看，当前复盘块完成了“记录”，但还没有完成“可分享”。

从设计角度看，当前复盘块的信息层级也还不够清楚：

- `summary`
- `suggestedNextAction`
- 形态统计
- 补充素材

这些内容现在是并排堆在一起的，导致用户不容易立刻理解：

> 我点一次复制，最终到底会拿到什么

### 新定位

这块后面应该明确成：

> **一键复制今天的复盘推文草稿**

不是复制内部日志，也不是复制系统说明。

### 新结构建议

#### 复盘卡片首屏

只保留四件事：

1. 一句简短标题
   - 例如：`今天的复盘草稿已经准备好`

2. 一段可直接发的推文预览
   - 3 到 5 行
   - 有自然断句
   - 不写系统口吻

3. 一行轻量统计
   - `短推 X · 线程 Y · 长文 Z`

4. 两个动作
   - `复制复盘`
   - `重置今天`

#### 折叠区

把下面这些收进折叠区：

- 最佳帖子 URL
- 最佳回复 URL
- 最佳内容形态

但折叠区的标题要改得更直白：

- 不叫“补充素材”
- 建议改成：`附上今天表现最好的链接（可选）`

### 推文草稿的文案方向

复制出去的草稿不应该继续用当前这种“系统总结句”：

- `今天完成率 58%。`
- `最值得继续的是……`
- `还剩 4 项没完成。`

这更像内部面板，不像可发布内容。

建议改成更适合发推的结构：

1. 第一行：今天的进展一句话
2. 第二行：形态产出
3. 第三行：最有效动作
4. 第四行：明天的重点

例如结构上更接近：

`今天打卡：完成率 58%，粉丝持平。`
`产出：短推 0 / 线程 0 / 长文 8。`
`今天最有效的是：大 V 互动 + 完成 22 次真实互动。`
`明天先补「选题收集」，继续把节奏做稳。`

如果补了最佳帖子或最佳回复链接，再附在最后。不显示最佳形态这种没意义的信息

### 设计原则

- 默认复制内容必须“能发”，不是“能看”
- 复盘块的首屏只做“预览 + 复制”
- 详细补充字段全部退到折叠区，自动保存已经填充的链接。
- 视觉上继续保持 `Raycast` 式的小而清楚，不再像小表单

## 4.7 互动计数说明补齐

这部分不改逻辑，但要说清楚。

### 保留当前逻辑

- `高质量回复`
  - 任何有效回复都会加

- `大 V 互动`
  - 只统计已入池、标签为 `对标学习`、且粉丝量级 `5k-10k` 及以上的互动

- `同生态互动`
  - 只统计已入池、标签为 `同生态` 的互动

### 这轮要做的事

把上面三条继续明确写进：

- 执行强度与每日数量
- 每项任务的一句话说明

避免用户继续猜测“为什么这次加了两个、那次只加一个”。

---

## 5. 这轮不做什么

为了避免范围继续失控，这轮先不做：

- 合并高质量回复 / 大 V 互动 / 同生态互动
- 重做整套阶段方法论
- 再新增一套更复杂的账号角色系统
- 再做更重的内容建议模块

这轮只把：

- 识别准
- 工具条顺
- 卡片统一

这三件事做好。

---

## 6. 实施顺序

按工作流，下一轮建议顺序是：

1. 先做内容识别重构
   - 长文发布会话
   - 自动保存排除
   - 调试记录

2. 再重构账号工作台工具条
   - 主工具条 / 筛选条分层
   - 全局搜索
   - 批量模式状态化

3. 再统一卡片结构
   - 已入池补 bio
   - 粉丝与量级统一
   - 移除低价值文案
