# Phase 7.6 交互简化优化方案

## 一、这轮要解决什么

这一轮不再新增大模块，重点解决“已经能用，但还是太重、太绕、太像后台表单”的问题。

核心目标：

1. 明确 `popup`、悬浮框、设置工作台三者分工
2. 让悬浮框收起态也有可读进度，并且继续支持拖动
3. 把“执行强度 + 每日数量”改成真正轻量的设置面板
4. 收紧账号角色标签，降低理解门槛
5. 重做候选处理和正式账号池的标签交互，减少多余控件
6. 去掉愚蠢的状态展示方式，改成按钮本身反馈

---

## 二、是否保留 popup

### 结论

**保留 `popup`，但继续做轻。不要把所有内容都并进设置工作台。**

### 原因

浏览器扩展本身就有一个标准入口。Chrome 官方的 `chrome.action` 设计，本来就是让用户从工具栏图标快速打开一个轻入口，而不是每次都跳到完整后台。

参考：

- [Chrome action API](https://developer.chrome.com/docs/extensions/reference/api/action)

从产品角度看，三层结构现在是合理的：

- **悬浮框**：执行时一直看着，负责进度和快速打卡
- **popup**：快速总览、健康状态、去哪里点下一步
- **设置工作台**：重操作、重管理、重编辑

如果把 `popup` 彻底取消，问题会变成：

1. 浏览器工具栏入口失去意义
2. 用户想快速看状态时，还得打开完整后台
3. 悬浮框不在的页面场景下，没有快速入口

### 本轮建议

不取消 `popup`，但把它收成：

- 当前完成率
- 当前阶段
- 页面是否已连接
- 一键打开设置工作台
- 一键显示 / 收起悬浮框

也就是说：

**保留 popup，但让它更像“快速入口”，不再像第二个后台。**

## 三、悬浮框优化

### 3.1 收起态也要显示进度条

当前问题：

- 收起态只显示百分比
- 信息不够直观

优化方向：

- 收起态改成一个小胶囊条
- 内容包含：
  - 百分比
  - 一条很细的进度条
  - 一句极短状态，例如“继续推进”

建议结构：

- 左：`42%`
- 中：细进度条
- 右：短状态文案

这样收起后仍然能一眼看进度，而不是只有一个数字。

### 3.2 收起态也要能拖动

当前问题：

- 展开态可拖
- 收起态不可拖

优化方向：

- 收起态整个胶囊都可拖
- 展开态仍然只允许顶部拖动
- 两种状态共用同一套位置存储

### 3.3 悬浮框继续保留全部任务

你已经明确要求保留全部任务，这个本轮不再收回。

但为了不让面板过高、过重，建议继续做这些控制：

- 单行任务展示
- 更细的进度条
- 更轻的 `+ / -`
- 任务列表区域单独滚动

## 四、执行强度与每日数量重做

### 当前问题

你说得对，当前这一块做得太重了：

- 预设太像一组大卡片
- 每个任务也是厚重块
- 整体很像在填一张复杂表单

### 新方案

改成一个非常简单的设置块：

#### 第一行：强度切换

- `保守`
- `标准`
- `强执行`
- `自定义`

形式：

- 一排轻量分段按钮
- 不再做大卡片

#### 第二部分：每日数量

用紧凑列表，不要大块卡片：

- `短内容输出    [ 1 ]`
- `长文          [ 1 ]`
- `高质量回复    [ 8 ]`
- `大 V 互动     [ 2 ]`

交互规则保持你认可的这套：

1. 点击 `标准`
   - 所有输入框自动填成标准值
2. 点击 `强执行`
   - 所有输入框自动填成强执行值
3. 用户手动改任意一个输入框
   - 自动切到 `自定义`
4. 保存后
   - 立即重建今天的任务目标
   - 已完成进度保留

### 状态反馈怎么改

不再做单独的右上角“当前状态 / 当前反馈”模块。

改成：

- 保存按钮点击后显示 `保存中...`
- 成功后短暂变成 `已保存`
- 套用预设时，按钮或分段控件本身给反馈

这才是正常产品该有的反馈方式。

## 五、账号角色标签是否继续精简

### 当前问题

现在的角色标签有：

- `同生态`
- `对标学习`
- `选题来源`

而你的真实判断是：

- 大多数人不会认真区分“对标学习”和“选题来源”
- 分太细以后，大家反而不会用

### 现有“选题来源”为什么很少出现

当前代码里，`选题来源` 的判断条件主要是 bio 里命中这些词：

- `研究`
- `资讯`
- `新闻`
- `观察`
- `趋势`
- `拆解`
- `复盘`
- `评论`
- `newsletter`
- `writer`
- `analyst`
- `research`

对应位置在：

- [phase-seven-data.ts](/D:/myapp/ai_program/tmp/twitter-web-exporter/src/extension/growth-system/phase-seven-data.ts)

这说明两件事：

1. 它现在确实是一个比较窄的判断口径
2. 它在产品层的价值没有大到值得让所有用户都承担理解成本

### 建议结论

**本轮建议把顶层角色标签从 3 个收成 2 个：**

- `同生态`
- `对标学习`

而 `选题来源` 不再作为正式主标签，改成：

- 后台辅助信号
- 或未来的可选次级标签
- 但先不放在第一层交互里

这样会简单很多。

### 为什么这样更合理

因为多数用户真实心智是：

1. 这个人是不是我同生态的人
2. 这个人是不是我想对标的人

这已经足够支撑大部分使用场景。

## 六、候选处理与正式账号池重做

这一块我建议参考三类成熟产品，不再自己空想：

- [Linear Filters](https://linear.app/docs/filters)
- [Airtable Views](https://support.airtable.com/v1/docs/getting-started-with-airtable-views/)
- [GitHub Issues](https://github.com/features/issues)

### 我们真正借什么

#### 1. 借 Linear

借它的：

- 过滤条很轻
- 不把每个筛选都做成一大块控件
- 让“筛选”和“列表”分层清楚

#### 2. 借 Airtable

借它的：

- 一份数据，多种视图
- 候选处理和正式账号池本质上是不同视图，不是两套大后台

#### 3. 借 GitHub Issues

借它的：

- 勾选后再出现批量操作条
- 默认状态尽量安静
- 列表本身可快速操作

### 本轮重构方向

#### 6.1 候选处理

去掉：

- 大段建议理由
- 大块状态卡
- 独立“当前反馈”模块

改成：

- 顶部轻量筛选
- 列表卡片更扁
- 用户名旁边就是可操作标签

#### 6.2 正式账号池

去掉：

- 单独的“角色标签下拉块”
- 单独的“粉丝量级下拉块”
- 一整排复杂按钮

改成：

- 用户名右侧直接挂两个小标签
  - `角色标签`
  - `粉丝量级`
- 标签本身就是小下拉
- 右侧只留一个轻量操作入口
  - 例如 `···`
  - 点开再选：打回待处理 / 忽略 / 删除

也就是说：

**标签本身直接可改，额外操作收进一个轻菜单。**

### 为什么这样更合理

因为现在的问题不是“能力不够”，而是：

- 太多控件同时存在
- 太多块状信息抢注意力
- 太像后台配置表单

本轮目标就是让它像一个成熟列表，而不是像一页表单。

## 七、批量操作反馈怎么改

### 当前问题

比如：

- 点击“全选当前页待处理”
- 突然冒出来一块“已勾选四个候选账号”

这种反馈确实突兀。

### 新方案

参考 GitHub / Linear 风格：

- 平时不显示批量条
- 一旦勾选，列表顶部浮出一条轻量操作条
- 只显示必要动作

例如：

- `已选 4 项`
- `加入`
- `改标签`
- `忽略`
- `清空`

不要再做成一个单独大卡片。

---

## 八、标签交互怎么改

### 目标

让用户尽可能少地点、多改成、少切上下文。

### 建议方案

每个账号卡片上：

- 用户名后直接跟两个轻标签
  - `同生态 / 对标学习`
  - `1k-5k / 5k-10k`

交互方式：

- 点角色标签，直接弹出小菜单切换
- 点粉丝量级标签，直接弹出小菜单切换

这样你就不需要再单独给一块：

- 角色下拉框
- 粉丝量级下拉框

### 右侧操作简化

右侧只保留一个轻量操作入口：

- `···`

点开后再出现：

- 打回待处理
- 移到忽略
- 删除

这样列表就会干净很多。

## 九、审美和界面风格定稿

这一轮不再保留多个平行方向，直接定稿为：

- **整体风格主参考：Linear**
- **轻入口与小面板细节参考：Raycast**
- **列表勾选与批量操作参考：GitHub Issues**

也就是说，后续开发时不再自己发明一套后台风格，而是直接按这三者的职责拆分去实现。

### 9.1 主参考：Linear

官网：

- [Linear](https://linear.app/)
- [Linear Filters](https://linear.app/docs/filters)

选择它作为主参考的原因：

1. 它最接近这个插件的真实定位  
   不是展示型网站，不是内容社区，而是高频、克制、效率型工具。

2. 它的界面很轻，但信息密度高  
   特别适合任务列表、标签、小筛选器、轻量工具栏。

3. 它不会把页面做成一堆大卡片  
   这正是当前插件最需要纠正的地方。

后续所有主界面默认向 Linear 看齐：

- 页面结构
- 留白方式
- 标签密度
- 过滤条样式
- 列表视图层级

### 9.2 辅参考一：Raycast

官网：

- [Raycast](https://www.raycast.com/)

选择它的原因：

1. `popup` 本质上就是一个轻入口  
   Raycast 很适合参考这种“小而快”的工具入口。

2. 悬浮框也需要“轻、小、安静”  
   不能像后台，不应该抢页面内容。

3. 它对小按钮、小面板、小状态提示的处理非常克制

后续借它的地方：

- `popup` 的整体感觉
- 悬浮框收起态
- 轻按钮
- 细状态反馈

### 9.3 辅参考二：GitHub Issues

官网：

- [GitHub Issues](https://github.com/features/issues)

选择它的原因：

1. 它的列表勾选逻辑成熟  
   非常适合候选处理和正式账号池。

2. 它的批量操作不会突兀  
   勾选后再出现，而不是页面里一直摆着一堆大操作块。

3. 它适合借“右侧轻菜单”的处理思路

后续借它的地方：

- 勾选后浮出批量条
- 列表顶部操作区
- `···` 轻量操作菜单
- 状态切换方式

### 9.4 本轮不再作为主参考的方向

以下方向本轮不再作为主参考，只保留原则级借鉴：

- Apple：保留“克制”和“轻工具栏”原则，但不直接照搬视觉
- Airtable：保留“多视图”结构思路，但不照搬表格感

原因很简单：

- Apple 更像系统设计原则，不是这个插件的直接产品模板
- Airtable 的表格感还是偏重，不适合你要的轻工具型界面

### 9.5 具体界面该向谁看齐

为了避免后面又重新发明，这里直接写死：

#### 悬浮框

- 主体：`Raycast`
- 结构：`Linear`

要求：

- 更轻
- 更薄
- 更像一个执行条
- 不做厚重块状卡片

#### popup

- 主体：`Raycast`

要求：

- 更像快速入口
- 不像第二个后台
- 信息少而关键

#### 设置工作台

- 主体：`Linear`

要求：

- 不做后台管理模板风
- 不做大卡片堆叠
- 工具栏式筛选
- 列表优先

#### 候选处理 / 正式账号池

- 主体：`Linear`
- 批量与勾选细节：`GitHub Issues`

要求：

- 标签本身可操作
- 勾选后再出现批量条
- 操作入口极简

### 9.6 视觉执行原则

既然已经定了参考，那后续视觉上也要统一：

1. 不再使用厚重的说明块
2. 不再使用大面积重复卡片
3. 不再把状态反馈单独做成一块“当前状态”区域
4. 标签必须更轻、更小、更精致
5. 筛选器必须像工具栏，不像表单
6. 列表中的操作要收敛到最少

### 9.7 最终推荐

如果只用一句话定调：

**整体界面向 Linear 看齐，悬浮框和 popup 借 Raycast，列表交互借 GitHub Issues。**

这就是后续开发的统一设计基线。

3. 收起态支持拖动

1. 顶层角色只保留 `同生态 / 对标学习`

## 十一、实施时会使用的 skills

为了避免后面开发时又临时换风格、换做法，这里把预计会用到的 skills 先写清楚。

### 11.1 `frontend-design`

用途：

- 用来约束整体界面重构
- 把 `Linear / Raycast / GitHub Issues` 这套风格真正翻成具体界面
- 控制以下重点区域：
  - 悬浮框轻量化
  - `popup` 收口
  - 设置工作台重排
  - 候选处理与正式账号池的视觉层级

这会是本轮**最核心**的 skill。

使用方式：

- 在真正开始改界面前，先按本方案固定主风格
- 实施中优先让组件、间距、标签、按钮、筛选条都向这套风格收敛

### 11.2 `playwright-automation`

用途：

- 用来验证界面改完后没有把交互链路改坏
- 重点覆盖：
  - 悬浮框是否显示
  - 收起态是否仍可显示进度
  - 收起态是否还能拖动
  - `popup` 是否还能正常打开和显示
  - 候选处理 / 正式账号池的标签修改、批量操作是否还能走通

这会是本轮**主要验证**用的 skill。

使用方式：

- 每完成一轮界面重构后，跑自动化检查
- 如果自动化发现结构变化导致脚本失效，再同步更新测试脚本

### 11.3 本轮不作为主力使用的 skills

以下 skills 本轮不会作为主力：

- `plugin-creator`
  - 原因：当前不是新建插件，而是在现有 Chrome 扩展上迭代

- 其他与图片、文章、Cloudflare、Android 等无关 skills
  - 原因：和这轮任务无关

### 11.4 结论

本轮实施建议固定为：

- **设计收敛：`frontend-design`**
- **自动化验证：`playwright-automation`**

这样做会更稳，也更快。

做完后，应该满足这些标准：

1. `popup` 仍存在，但明显更轻
2. 悬浮框收起态能显示进度条，并可拖动
3. 执行强度区域明显变轻，不再像一块大后台卡片
4. 每日数量区域变成紧凑列表
5. 顶层账号角色只剩两个，用户更容易判断
6. 候选处理和正式账号池的标签可以直接点改
7. 不再出现单独的大状态反馈块
8. 列表整体更像成熟工具，而不是表单堆叠

这轮最重要的不是再加功能，而是把整个产品从“功能已经不少，但用起来重”拉回到：

- 更轻
- 更直接
- 更像成熟工具
- 更符合普通用户的真实判断方式
