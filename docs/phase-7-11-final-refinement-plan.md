# Phase 7.11 最终优化实施方案

更新日期：2026-05-16

## 1. 这份方案解决什么

这份方案把前面几轮已经确认过、但还没有完全收顺的修改项统一合并，作为下一轮开发的唯一依据。

本轮只做三类事情：

1. 内容识别收口
2. `popup` 每日复盘和文案收口
3. 账号工作台结构与交互收口

这轮**不再新增新功能**，目标是把已有能力做准、做顺、做轻。

---

## 2. 本轮工作流

这轮继续按固定工作流执行：

1. 先评估当前问题是否真实存在
2. 再确认哪些该保留、哪些该删
3. 再统一产品结构
4. 再按既定风格实施
5. 实施后做自动化验证
6. 验证失败自动返修，最多 3 轮

本轮会继续沿用：

- `frontend-design`
  - 负责界面语言、布局层级、信息密度收口
- `playwright-automation`
  - 负责改完后的自动化验证

视觉和交互基线继续保持：

- 整体风格：`Linear`
- 轻面板与 `popup`：`Raycast`
- 列表、批量模式、轻操作条：`GitHub Issues`

---

## 3. 当前问题总结

## 3.1 内容识别

当前还有两个核心问题：

1. 普通短内容在某些情况下仍可能被误判成长文
2. `Article` 自动保存和真正发布没有彻底区分

这说明当前识别逻辑还不够“发布结果导向”，而仍然混入了一部分页面上下文猜测。

## 3.2 popup 每日复盘

当前每日复盘的问题不是没有价值，而是：

- 文案还像系统摘要，不像能直接发的推文
- 有些说明文字太多余
- `最佳形态` 没有足够价值
- 折叠区文案太重

## 3.3 账号工作台

当前账号工作台的问题集中在三类：

1. 工具条层级不够统一  
   - 状态切换  
   - 搜索框  
   - 筛选器  
   - 批量模式  
   - 手动添加账号  
   这几类控件还没有完全分层

2. 三个状态页的语言还不够一致  
   - `待处理`
   - `已入池`
   - `已忽略`

3. 批量模式交互还不够顺  
   - 小复选框点击范围小
   - 进入批量后选择动作不够自然

## 4. 最终产品决策

## 4.1 内容识别

本轮正式定死：

- `Article` 才算长文
- 明确线程才算线程
- 其他原创内容统一算短内容

并且：

- 自动保存不算长文发布
- 草稿同步不算长文发布
- 只有真正点击发布并确认成功后，长文才加一

这轮不再继续容忍“文章页里的中间请求也算长文”。

## 4.2 popup

`popup` 继续保留，但只保留真正有用的概览信息。

本轮重点只改：

- 每日复盘块

其余 `popup` 结构不再大改。

## 4.3 账号工作台

账号工作台继续保留统一页面结构，不拆回两套或三套后台。

正式定死：

- 一个全局搜索框
- 一套统一筛选器
- 三个状态视图：
  - `待处理`
  - `已入池`
  - `已忽略`
- 批量模式保留，但默认关闭
- 手动添加账号保留，但改成全局入口

## 5. 内容识别最终方案

## 5.1 规则定义

### 长文

只有满足下面所有条件时才记一次长文：

1. 当前是 `Article` 发布链路
2. 用户明确触发了发布动作
3. 页面世界里捕获到对应的成功发布确认
4. 该发布会话还没记过账

### 不计数的情况

下面这些全部不算长文：

- 自动保存
- 草稿同步
- 编辑过程中的中间态请求
- 普通短推发布

### 短内容

只要不是：

- `Article`
- 明确线程

那就统一按短内容处理。

## 5.2 覆盖范围与漏判控制

这轮长文识别不能只追求“不要误判”，还要同时控制“不要漏判”。

### 核心判断

新的长文识别不会只依赖“当前是不是文章编辑页”这一个条件。

它会同时看三类信号：

1. **创作场景信号**  
   用户当前是否进入了 `Article` 编辑和发布流程

2. **显式发布信号**  
   用户是否真的触发了 `Publish`

3. **发布成功信号**  
   页面世界里是否拿到了对应的成功结果

### 为什么这样更稳

如果只看编辑器场景，容易把自动保存误判成发布。  
如果只看网络请求，又可能在某些界面实验或发布路径变化时漏掉真正的发布。

所以这轮改成：

- **主判定**：显式发布信号 + 成功响应确认
- **兜底判定**：发布后页面结果变化确认

### 兜底规则

为了降低漏判，本轮增加一个“发布后兜底确认”：

如果出现下面这种情况：

1. 用户已经明确触发 `Publish`
2. 页面随后进入文章已发布状态
3. 文章结果页或文章链接已经生成
4. 同时页面世界里出现匹配的文章结果数据

那么即使第一条网络确认没有完全命中，也允许作为一次有效长文发布处理。

也就是说：

- 不会只靠编辑器状态记账
- 也不会只靠单一请求名记账
- 会采用“发布动作 + 成功结果”的双确认模型

### 结论

这套方案的目标不是覆盖 100% 理论边界，而是：

- 覆盖绝大多数真实 `Article Publish` 场景
- 避免自动保存误记
- 尽量降低因为发布链路差异导致的漏记

## 5.2 实施要求

这轮不再继续只靠内部猜测修补，而是继续按“发布确认制”收口：

1. 页面创作模式识别
2. 页面真实发布请求确认
3. 成功后单次记账
4. 同一发布会话不重复加数

并且补充：

5. 发布后页面结果兜底确认

## 5.3 开源参考与复用策略

这轮不再继续完全靠本地小修小补，而是明确复用外部成熟路线。

### 主参考一：`baoyu-post-to-x`

参考：  
[baoyu-post-to-x](https://github.com/JimLiu/baoyu-skills#baoyu-post-to-x)

本轮重点借它已经验证过的真实长文发布前链路：

- 进入 `x.com/compose/articles`
- 定位长文编辑器
- 定位 `Preview / Publish` 按钮
- 真实浏览器里的长文发布操作顺序

这条路线不负责插件记账，但负责提供“用户到底怎样才算真的进入长文发布动作”的稳定前提。

### 主参考二：`twitter-web-exporter`

参考：  
[twitter-web-exporter](https://github.com/prinsss/twitter-web-exporter)

本轮重点借它的页面世界请求拦截思路：

- 页面世界请求拦截
- 真实 GraphQL / fetch / XHR 结果确认
- 不只靠扩展隔离环境猜测

这条路线会作为长文发布成功确认的主参考。

### 次参考：`x-algorithm-score`

参考：  
[x-algorithm-score](https://github.com/affaan-m/x-algorithm-score)

本轮只借它的前半段思路：

- composer / 编辑区状态识别
- 当前用户正在做哪种创作动作

不把它当成最终发布成功确认方案。

### 复用原则

最终组合是：

1. 发布动作和编辑器选择器：复用 `baoyu-post-to-x`
2. 页面世界网络确认：复用 `twitter-web-exporter`
3. 编辑区状态辅助：参考 `x-algorithm-score`
4. 记账策略：我们的“发布确认制 + 兜底确认”

### 不再继续走的路线

这轮正式放弃下面这些不稳的做法：

- 只靠“当前在文章页里”判断长文发布
- 只靠某一个按钮文案猜是不是 `Publish`
- 只靠某个请求名模糊命中就记账
- 继续用本地构造事件替代真实发布链路

## 6. popup 每日复盘最终方案

## 6.1 保留什么

保留：

- `每日复盘` 标题
- 一段复盘预览
- `复制复盘` 按钮
- 一个折叠区，用来补充链接

## 6.2 删掉什么

本轮明确删除：

- `复制后就能直接发`
- `今天这条复盘可以直接发`
- `选择最佳内容形态`
- `最佳形态`
- 与最佳形态相关的复制内容

这些都属于冗余信息，不再保留。

## 6.3 首屏结构

首屏只保留：

1. 标题：`每日复盘`
2. 一段可复制的复盘草稿
3. 一个主按钮：`复制复盘`
4. 一个次按钮：`重置今天`

不再加额外说明句。

## 6.4 折叠区结构

折叠区标题统一改成：

- `附录`

折叠区内部只保留：

- `最佳帖子 URL`
- `最佳回复 URL`
- `保存附录`

不再出现：

- 最佳形态
- 解释性长文案

## 6.5 复盘文案方向

复制出来的文本要更像一条能直接发出去的推文，而不是系统日报。

目标表达方向：

```text
今天打卡 63%，粉丝持平。
输出 1 条线程，8 条长文。
今天最有效的是大 V 互动，一共完成了 23 次真实互动。
明天先补齐选题收集，优先写《这周做了什么》。
```

要求：

- 句子短
- 信息顺序固定
- 不出现双标点
- 不出现系统口吻
- 不堆解释

## 6.6 是否需要可编辑

本轮结论：

- **不需要**

理由：

- 这个位置只负责预览和复制
- 真要改，用户复制到 X 编辑器里改更自然
- 在 `popup` 里再做编辑，只会让这块重新变重

## 7. 账号工作台最终方案

## 7.1 整体结构

工作台继续做成一个统一页面，但工具条固定分成两层。

### 第一层：主工具条

只放：

- `待处理 / 已入池 / 已忽略`
- 全局搜索框
- `批量处理`
- `手动添加账号`

### 第二层：统一筛选条

三种状态页全部统一保留：

- `全部来源`
- `全部标签`
- `全部粉丝量级`
- `清空筛选`

这里正式定死：

- `已入池` 也必须保留来源筛选
- 不再允许某个状态页少一个筛选项

这样三种状态页的筛选结构才会完全一致。

## 7.2 搜索框规则

工作台只保留**一个全局搜索框**。

要求：

- 切换 `待处理 / 已入池 / 已忽略` 时，搜索词保留
- 标签筛选保留
- 来源筛选保留
- 粉丝量级筛选保留
- 只是结果集切换

## 7.3 批量模式最终交互

批量模式继续保留，但正式改成“模式切换”，不是普通按钮。

### 默认状态

- 不显示复选框
- 卡片正常浏览和单条操作

### 点击 `批量处理` 后

进入批量模式时：

- 不再显示小复选框作为主交互
- 改成**整张卡片可点击选中**
- 选中后整张卡片出现明显高亮、描边或选中状态
- 再点一次卡片取消选中

也就是说：

- 选择主交互 = 点击卡片本身
- 不是去点很小的复选框

### 批量条内容

进入批量模式后出现一条轻量操作条，顺序固定为：

1. `已选 N 个`
2. `全选当前页`
3. `全选筛选结果`
4. `清空`
5. `加入账号池`
6. `设为同生态`
7. `设为对标学习`
8. `忽略 / 恢复`
9. `退出批量`

## 7.4 手动添加账号

本轮正式定死：

- `手动添加账号` 是全局入口
- 放在主工具条右侧
- 点击一次打开
- 再点一次同一个按钮就收起

不再保留单独的“收起”按钮。

### 语义规则

- 这是一个 toggle
- 不是“打开后再找另一个按钮关闭”的双按钮交互

## 7.5 卡片结构统一

三种状态页卡片统一使用一套字段顺序：

1. 用户名 + 主标签
2. handle
3. bio
4. 具体粉丝数 + 粉丝量级 + 来源
5. 次信息
6. 操作区

### 统一规则

- 优先显示真实 `bio`
- 优先显示具体粉丝数
- 同时保留粉丝量级标签
- 不再显示：
  - “量级明显更高”
  - “更适合作为对标对象”
  - 其他解释性无效文案

## 7.6 主标签规则

主标签继续只保留：

- `同生态`
- `对标学习`

不再把 `选题来源` 当主标签。

## 8. 这轮不做什么

为了避免继续返工，这轮明确不做这些：

- 不在 `popup` 里做复盘编辑器
- 不新增新的账号角色标签
- 不把批量模式默认展开
- 不在卡片上加解释性说明文案
- 不继续保留 `最佳形态`

## 9. 实施顺序

本轮按下面顺序实施：

1. 先修内容识别  
   - 长文只在真正发布后加一  
   - 自动保存不记

2. 再改 `popup` 每日复盘  
   - 去掉多余文案  
   - 去掉最佳形态  
   - 改成更像能直接发的复盘草稿

3. 再重构账号工作台工具条  
   - 主工具条  
   - 筛选条  
   - 已入池补来源筛选

4. 再改批量模式交互  
   - 去掉小复选框主交互  
   - 改成整卡片选中

5. 最后统一卡片语言与细节

## 9.1 长文识别专项测试策略

这轮长文识别不能只靠本地构造事件验证，必须补真实链路测试。

### 第一层：现有自动化脚本

继续保留并扩展：

- 扩展主流程冒烟脚本
- 长文识别专项脚本

这层负责快速回归：

- 自动保存不记长文
- 真正发布后长文加一
- 短内容不误记成长文

### 第二层：真实发布辅助验证

这轮把 `baoyu-post-to-x` 作为真实发布链路的辅助验证手段。

参考技能：

- `baoyu-post-to-x`

用途：

- 用真实 Chrome 打开 X Article 发布流程
- 自动填充文章内容
- 走真实发布前链路
- 再配合我们自己的扩展识别逻辑观察是否正确记账

### 注意

`baoyu-post-to-x` 的文章发布脚本本身是“真实浏览器 + 自动填充 + 用户最终确认发布”的模式。  
所以它最适合作为：

- 真实页面链路验证
- 发布前后状态观察
- 识别逻辑的实机回归辅助

而不是单独替代我们自己的记账逻辑。

### 这轮测试目标

实施后至少要验证这 4 类场景：

1. 进入 Article 编辑页但只触发自动保存  
   - **不加长文**

2. 完成 Article 填充但不点击 Publish  
   - **不加长文**

3. 真正点击 Publish 并发布成功  
   - **长文 +1**

4. 发布普通短内容  
   - **只算短内容，不算长文**

### 测试失败后的返修策略

如果以上任何一类场景失败：

1. 先看最近发布事件缓存
2. 确认是：
   - 发布意图没捕获到
   - 成功响应没命中
   - 兜底结果确认没命中
   - 或去重逻辑挡掉了
3. 按失败类型返修
4. 重新跑自动化和真实辅助验证
5. 最多返修 3 轮

## 9.2 Codex 内可直接辅助这轮工作的能力

### 可选辅助

1. `GitHub` 插件  
   - 适合继续查看参考仓库代码和历史结构
   - 对这轮有帮助，但不是必需

### 结论

这轮关键不是再找新的开发插件，而是：

- 复用 `baoyu-post-to-x`
- 复用 `twitter-web-exporter`
- 用 `playwright-automation` 做回归验证
